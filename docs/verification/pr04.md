## Production architecture and ownership

`frameScheduler.ts` owns frame arrival, deduplication and one deferred execution.
It prefers paired requestVideoFrameCallback/cancelVideoFrameCallback. A positive
presentedFrames count identifies progress even with coarse mediaTime; finite
nonnegative mediaTime is the fallback identity for a zero count. RAF fallback
prefers a positive finite getVideoPlaybackQuality totalVideoFrames count, then
finite nonnegative currentTime. There is **no configured inference rate cap**.
currentTime-only browsers may have coarse timestamps and cannot prove decoded
frame identity as precisely; rapid distinct frames sharing a timestamp can be
coalesced. First zero-time frames are accepted, and identity is fresh for every
camera/model/scheduler session, including a new scene at the same timestamp.

One pending bit represents the latest live video candidate; repeated arrivals
replace its opportunity to run and never allocate a frame queue. At most one
execution per scheduler and one owned lock across scheduler generations can run.
Every lock acquisition has a unique job token; only that execution's finish can
release it. Cleanup cancels its callback/timer and pending candidate, and cannot
release another job. Promise doubles exercise completion after cancellation and
slow work; the real MediaPipe call remains **synchronous on the main thread**.
Neither rVFC nor the zero-delay timer provides worker execution.

VisionCanvas checks active model/readiness, engine model/requestId, camera
readiness/requestId and a separate scheduler generation at reservation, execution
and adoption. Video readyState and positive dimensions are independent gates.
A layout-owned generation invalidates work before passive cleanup on scene or
threshold changes and on teardown. The camera hook still owns only its own
stream; App still owns the selected engine task. Stop/restart does not recreate
a ready model. clearDetections resets temporary outputs/mask/smoothing state only,
without disposing the model or changing its initialization generation. A separate
output generation also rejects scene state cleared reentrantly during an SDK call.

The overlay RAF is independent of input callbacks. It draws the latest valid
result through the current committed appearance/selection/ripple function.
Appearance/callback/TTS changes do not restart acquisition. Confidence threshold
changes deliberately clear scene output and create a new scheduler window;
model/camera acquisition remains unchanged. No exhaustive-deps suppression remains
in VisionCanvas. Transient results and measurements stay outside React; snapshots
and dirty detection-list/parent updates publish at most every 250 ms while running.
Parent notifications happen only for new inference results or invalidation. TTS
checks happen once per newly adopted inference, rather than once per overlay RAF.

## Failure behavior

SDK inference errors reset narrow temporary engine state, invalidate latest
output, exclude failed work from successful inference counts, and permit the next
new frame to recover. An unchanged failed frame is not retried automatically.
Diagnostics log at most once per scheduler session; sustained failures show an
inference error at the next HUD publication. Successful recovery clears it.
The engine itself repairs temporary state even for callers outside the canvas.
A stale engine execution cannot publish success or clear a replacement task's
outputs. Existing successful-empty smoothing behavior is otherwise retained.

Drawing, parent-notification and TTS exceptions deliberately stop both loops,
clear the scene/list/visible overlay, and expose a Japanese error and explicit
`処理を再試行` button. Retry creates a fresh scheduler/measurement window while
retaining the camera and ready model. There is no infinite side-effect retry.
Tap-selection/TTS exceptions use the same visible stopped state. Camera and model
errors retain their existing separate recovery controls. Unmount cancels pending
frame, draw, timer and ripple callbacks. Tests cover StrictMode teardown and
synchronous reentrant generation invalidation as well as async job completion.

## Measurement contract

All measurements use a React-independent PerformanceMetrics collector and a
monotonic performance.now clock. Named constants are in performanceMetrics.ts.

| Measurement | Included work | Estimator / minimum |
| --- | --- | --- |
| Inference FPS (`推論`) | Successful valid-generation detectVideoFrame completions, including empty results | 1000 × (N−1) / (last−first), at least 2 distinct completion timestamps spanning 250 ms |
| Overlay draw FPS (`描画`) | Successful completed offscreen overlay and visible-copy operations, including successful empty overlays | Same event-span estimator; blank clears, missing contexts, callbacks without a valid result, and failed draws do not count |
| Frame processing (`フレーム処理`) | Elapsed time immediately around the **entire** detectVideoFrame call: SDK, mask conversion, filtering, smoothing and result cleanup | Arithmetic mean of positive valid durations; minimum 1 duration |

There is a trailing **5000 ms** retention window, independently bounded to the
latest **300 entries per series**. High event rates can therefore shorten the
represented span. Each operation and snapshot performs O(300) bounded work; no
unbounded history exists. FPS is an event-span estimate, **not** throughput divided
by a fixed elapsed 5-second denominator, camera FPS or display refresh rate.
Drawing the same valid result again counts as a real draw, without counting a new
inference or another TTS decision. Observed rates are never clamped to a cosmetic
range; the deterministic test explicitly retains 1000 FPS.

The HUD timer takes a fresh clock snapshot every **250 ms**, even without incoming
frames. FPS and processing duration become unavailable when their last successful
event is at least **2000 ms** old; all samples expire after 5000 ms. Input is marked
stalled after **2000 ms** without a new video candidate, including no initial
candidate after scheduler readiness. Hidden-tab timer throttling can delay UI
publication, but the next actual clock snapshot expires the data before rendering
it again. Backward clock discontinuity clears all windows; invalid/negative clock
values produce unavailable output. Nonfinite/negative times and negative durations
are rejected. Zero-duration calls still count as successful events but provide no
duration measurement; identical completion timestamps provide no rate interval.
Nonpositive rate intervals are never divided.

Null is shown as `未計測`; zero/one samples or too short a span do not fabricate
0.0. This event-span estimator has no justified numeric-zero idle estimate, so
idle/stalled output is unavailable rather than measured zero. UI separately labels
loading, camera preparation, stopped, model/runtime error, input stalled and active
measurement. Windows reset across model, camera, threshold and retry generations.
The existing GPU delegate requested/initialized versus actual GPU utilization
unmeasured distinction remains. Frame processing is neither SDK-only nor GPU time.
