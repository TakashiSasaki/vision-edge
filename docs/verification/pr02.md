## State, failures and resource ownership

Each mounted App owns its own `VisionEngine` (a supplied instance is also an App
lifetime dependency for tests). There is no mutable engine singleton. A small
typed factory exposes fileset preparation and the two SDK task creation methods;
tests control these boundaries while using actual engine/state/UI code.

Model states are `idle / loading / ready / error`. They carry model/request ID;
ready also records the GPU delegate passed to creation; error records stage and
original cause. The stages are `wasm` for fileset/runtime preparation and `task`
for SDK task creation. **FilesetResolver resolves asset paths; the SDK can still
load WASM/loader/model resources inside createFromOptions.** Such failures are
task-stage errors with the original SDK cause, not evidence that WASM loaded.
The UI gives short Japanese failure text; console diagnostics retain model,
stage and cause. Offline browser tests accept either failure phase; controlled
unit tests independently exercise both phases.

Only the selected model is created. A same-model loading request receives the
same in-progress Promise; ready requests reuse the active task. An error can be
retried explicitly and does not permanently retain a failed initialization.
There is no per-frame initialization or automatic retry.

There is one active task and no task cache. Every selection/disposal advances the
engine generation. A replaced active task is closed. An obsolete task completion
is closed without publishing ready; obsolete failures cannot replace current
state. A finally block only clears its own pending generation. Disposal is
idempotent for task cleanup and permits React StrictMode-style setup again.
The SDK has no cancellation hook here, so in-flight creation/download may finish
after cancellation; the result is then closed. This does not abort network work.

Readiness is checked both at the real canvas bridge and engine entry. A mismatched
model or unready video returns `not-ready`, distinct from a successful empty
frame. A genuine inference exception is not converted by the engine into empty
success; the bridge logs it and invalidates its result. SDK result cleanup retains
diagnostics. Ready is never called camera-ready or inference success.

Model selection immediately clears the App's last frame and selection. Engine
temporal buffers/mask canvas are reset. A layout effect clears the visible old
overlay before paint. Results carry model/request ID, and UI accepts only the
current generation. The detection panel displays unacquired/waiting state until
a genuine current frame is available; it does not show normal zero detections
while initializing, failed, stopped, or before first inference.

## Minimal loop connection and deferrals

Adding model readiness necessarily restarts the existing effect when state or
request generation changes. Its one pending timer is therefore cancelled during
cleanup, and its inference flag released; otherwise an obsolete early return
could prevent the ready replacement model from ever running. A callback checks
the captured request before dispatch. Regression tests prove both cancellation
and positive inference after replacement. This is the minimum PR-02 connection,
not a new scheduler, worker or performance implementation.

The existing single drawOverlays exhaustive-deps exception is retained and
documented; no rule is broadened. Newly captured engine/readiness/request/onFrame
values are explicitly dependencies. The old clickRipple closure remains deferred.

PR-03 still owns camera callback stability, unnecessary reacquisition, late
getUserMedia resolution, facing-mode races and track release. Camera effect code
and inline callbacks are intentionally unchanged. New model-status updates can
still encounter that inherited parent-render/reacquisition issue. PR-04 still
owns repeated video frames, loop design, main-thread synchronous inference and
actual timing. Tracking, coordinate conversion, dictionary, TTS and real-device
acceptance remain separate work.
